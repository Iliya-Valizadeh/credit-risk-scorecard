# What's weak

The full list of limits. The README shows the top few. They are ranked by how much each
one could change the main result if it were fixed, with the largest first.

The main result has three parts. LightGBM ranks applicants better than logistic
regression, by 0.013 to 0.020 of [ROC-AUC](glossary.md#roc-auc). After [calibration](glossary.md#calibration), the predicted default
rates match the observed ones on the test part. At a 20% [decline rate](glossary.md#decline-rate), the model
catches about half of the applicants who later had payment difficulties. All three are
measured on one random test part of Kaggle's Home Credit data.

| Rank | Weakness | How much it could change the result | What was done |
|---|---|---|---|
| 1 | The split is random, not by time. The table has no application date, so the test rows come from the same period as the training rows | Large. On later applicants, ROC-AUC would likely fall, and calibration is the part most likely to break if the default rate moves. The size is unknown | Stated in the README and the model card. Nothing else yet. A split by time needs data this table does not have |
| 2 | The binned scorecard (the bank-standard [baseline](glossary.md#baseline)) is the second baseline now, but neither it nor LightGBM is tuned. The scorecard's bins, the [IV](glossary.md#iv) cut of 0.02 and the sign-drop rule were fixed by me before the full run and not searched over. It ranks below the plain logistic regression (0.743 against 0.752) and below LightGBM, so the baseline is no longer the weak point, tuning is | Medium. A tuned LightGBM or a hand-tuned scorecard could narrow or widen the 0.023 to 0.029 gap. No one has measured by how much | The scorecard is in `src/credit_risk_scorecard/woe_scorecard.py`, with its points table in `reports/scorecard_table.csv`. [ADR 0002](decisions/0002-lightgbm-scores-logistic-regression-is-the-baseline.md) still describes the first baseline |
| 3 | Only the application table is used. The bureau and previous-application tables are not, and `sql/features.sql` holds one commented example | Medium. More data would likely raise both models' ranking and change every number. Its effect on the gap between them is unknown | The README says so, and says that earlier versions wrongly claimed a SQL feature pipeline |
| 4 | The evaluation plan was written after the results. The split, the extra metrics, the calibrator and the decline rate were all fixed after results were seen, and the test part has been scored many times | Small to medium. The threshold and calibrators were set on the calibration part, not the test part. But a reader cannot check that no choice was steered by test numbers | [The eval plan](eval_plan.md) is labelled as written after the results and cites the commit behind each choice |
| 5 | The group results have no intervals. The gender and age tables, and the with-and-without-gender comparison, come from one split. Dropping `CODE_GENDER` moved ROC-AUC by less than the width of the headline interval | Medium for the fairness finding. The gaps between groups are several points wide, but no test says how much of each could be noise. The ROC-AUC cost of dropping gender may be noise | The README says the with-and-without comparison has no interval. Nothing else yet |
| 6 | Gender still reaches the model through other inputs. Age enters directly through `DAYS_BIRTH`. The group check covers gender and four age bands only | Large for the fairness finding, none for the ranking. Removing proxies or age could change both the gaps and the model's accuracy | Measured and reported in `reports/gender_check.md`. [ADR 0005](decisions/0005-drop-code-gender-as-a-model-input.md) records the drop of `CODE_GENDER`. No rule decides whether age may be used |
| 7 | The applicants are Home Credit's, not a Canadian lender's. The target is "payment difficulties", not a formal default definition | Large for any use at a real lender, none for the numbers on this data | Stated in the model card and the README. Both say the model is not for real lending, pricing or collections |
| 8 | The 20% decline rate has no cost analysis behind it. The expected-loss view rests on an assumed loss rate and exposure, in a currency the dataset does not name. That calibrated PDs match the outcome-implied loss is close to guaranteed, because the calibrator was fitted on data drawn the same way as the test part | Changes the numbers at the threshold and the [expected loss](glossary.md#expected-loss), not the ranking or calibration | Both are labelled illustrative in the README, and the expected loss also in `reports/results.md`. The README says the close match is expected, not a separate test. [ADR 0004](decisions/0004-operating-point-is-a-20-percent-decline-rate.md) records the choice |
| 9 | The intervals come from resampling the test rows only. They do not cover a new random split or a new seed | Small. The gap's interval would widen, but it sits well above zero now | Nothing yet |
| 10 | Missing values are filled in with no flag to say they were missing | Small. A flag might raise the ranking a little | Listed in the README. Nothing else yet |
| 11 | No model was trained without class weighting. So this repo can't say whether the weighting helped the ranking at all. The weighting is what pushed the raw scores up, so the large calibration gain mostly undoes a choice made here | Unknown for the ranking, probably small. None for the calibrated PDs | The README says the calibration step undoes a side effect of the weighting. Nothing else yet | <!-- not-a-claim -->
| 12 | No check in CI reruns the real evaluation, because the data can't be in the repo. The committed numbers were checked against a fresh run by hand (`f00d1ee`) | None today. A later change could break a number without CI noticing | `make eval` reruns everything when the data is present. Tests on synthetic data run in CI | <!-- not-a-claim -->
| 13 | `make demo` runs the real pipeline on synthetic applicants. Its numbers say nothing about the model's real performance | None for the result. A reader could mistake the demo's numbers for results | The demo's first printed line says the data is synthetic and the numbers are not the project's results | <!-- not-a-claim -->
| 14 | `models/pipeline.joblib` is not committed, so the Streamlit app does not run from a fresh clone | None for the result | Kept out because the file holds values computed from Kaggle rows. `make eval` rebuilds it. See [ADR 0001](decisions/0001-adopting-the-house-standard.md), decision 7 | <!-- not-a-claim -->
| 15 | Resolved on 2026-11-16. Test coverage of the package is 99%, and the build fails below that. High coverage does not show the code is right: the tests run on synthetic data and check structure and ranges, not the committed numbers (see rank 12) | Low. A wrong number could still pass the tests | The floor is set in `pyproject.toml` and only goes up. ADR 0001, decision 8, records the lower floor it replaced | <!-- not-a-claim -->
| 16 | Resolved on 2026-11-16. mypy now runs in strict mode on `src/` and `tests/`, set in `pyproject.toml`. Some libraries ship no type stubs, so calls into them are not fully checked | None for the result | `make lint` and CI enforce it. ADR 0001, decision 10, records the default mode it replaced | <!-- not-a-claim -->
| 17 | The scorecard's train-versus-test [PSI](glossary.md#psi) is near zero by construction, because both parts are random draws from one table. It shows the PSI code works, not that the score is stable over time | None for the ranking. Any claim of stability would be unearned | The README says so. A real drift check needs dated data, which this table lacks (see rank 1) | <!-- not-a-claim -->
| 18 | Dropping the 19 features with a negative coefficient is a greedy rule and was not checked against other selection rules. The binned scorecard's 0.743 depends on it | Small to medium for the scorecard, none for LightGBM | Reported in the README as a count. Not compared with other rules | <!-- not-a-claim -->
